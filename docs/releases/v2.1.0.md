## Русский

### Изменения

- Удаление и управление торрентами работают при открытии CleanArr по обычному HTTP в локальной сети: ключ идемпотентности теперь корректный UUID v4. Если браузер не даёт безопасного источника случайности, действие отклоняется с понятным сообщением.
- Перед удалением данных CleanArr проверяет файлы всех настроенных клиентов (qBittorrent, Transmission, Deluge, rTorrent). Если данные пересекаются с другой раздачей, в том числе cross-seed на другом клиенте, удаление блокируется с причиной `shared_path`. Если состав соседней раздачи неизвестен — с причиной `sibling_scope_unknown` и указанием этой раздачи.
- Торрент фильма удаляется, только если его hash не встречается в истории других фильмов ни в одном экземпляре Radarr. Иначе это pack, и удаление блокируется.
- Сопоставление с Radarr, Sonarr и Seerr отклоняется при противоречащих друг другу идентификаторах (`conflicting_identifiers`), а не подбирается по запасному идентификатору.
- Каскад из webhook Jellyfin выполняется, только если CleanArr подтвердил отсутствие объекта в настроенном Jellyfin. Без этого — `source_unverifiable`. Проверка начинается с точного поиска по ID.
- Выполненные удаления всегда остаются в результате и в журнале, даже если Seerr или другой сервис упал позже.
- Задача, в которой часть изменений уже применена, не повторяется автоматически и сохраняет исходную ошибку. Временные сбои до первого удаления повторяются с новой проверкой плана. Блокировки безопасности завершают задачу без повтора.
- Задача, у которой при запуске вся очистка оказалась заблокирована, больше не отображается как «Удаление завершено».
- Остановленный торрент rTorrent помечается причиной `torrent_closed`: запустите его, чтобы удалить данные.
- Торренты, оставленные политикой раздачи (`keep`/`defer`), записываются до удаления записи в Arr и отмечаются в разделе «Загрузки». Автоматического отложенного удаления пока нет.
- Запись в SQLite перенесена из event loop, соединения закрываются детерминированно. Коды ошибок задач хранятся в структурированном виде.

### Обновление и откат

Схема SQLite обновляется с 6 до 8: миграция 7 добавляет журнал оставленных торрентов, миграция 8 — коды ошибок задач. Схема конфигурации 4 не меняется. Перед обновлением с 2.0.4 сделайте и проверьте backup SQLite (`PRAGMA integrity_check` должен вернуть `ok`). Закройте старые предпросмотры и получите новые планы.

Откат: остановите CleanArr, сохраните базу схемы 8 под другим именем, восстановите backup схемы 6 и запустите образ 2.0.4. Версия 2.0.4 не открывает базу схемы 8. Подробности — в [руководстве эксплуатации](https://github.com/mambastick/Cleanarr/blob/v2.1.0/docs/OPERATIONS_RU.md) и [правилах безопасности](https://github.com/mambastick/Cleanarr/blob/v2.1.0/docs/SAFETY_RU.md).

Проверки на путях файлов сравнивают пути, которые сообщают клиенты. Разные точки монтирования и symlink для одних и тех же данных не распознаются, поэтому всем клиентам нужно одно пространство путей.

## English

### Changes

- Deletion and torrent controls work when CleanArr is opened over plain HTTP on a LAN: idempotency keys are now valid UUID v4 values. If the browser offers no secure random source, the action is refused with a clear message.
- Before removing data, CleanArr checks the files of every configured client (qBittorrent, Transmission, Deluge, rTorrent). Data that overlaps another torrent, including a cross-seed on another client, is blocked as `shared_path`. A neighbouring torrent whose files are unknown blocks overlapping targets as `sibling_scope_unknown` and is named in the plan.
- A movie's torrent is removed only if its hash does not appear in any other movie's history across all Radarr instances. Otherwise it is treated as a pack and blocked.
- Matching against Radarr, Sonarr and Seerr is rejected when identifiers contradict each other (`conflicting_identifiers`) instead of falling back to a weaker identifier.
- A Jellyfin webhook cascade runs only after CleanArr confirms the item is absent from the configured Jellyfin; otherwise it reports `source_unverifiable`. Verification starts with an exact ID lookup.
- Executed deletions always remain in the result and activity log, even when Seerr or another service fails later.
- A job that already applied part of its changes is not retried automatically and keeps its original error. Transient failures before the first deletion are retried with a fresh plan check. Safety blocks end the job without retry.
- A job whose cleanup was entirely blocked at run time is no longer reported as "Deletion completed".
- A stopped rTorrent torrent is reported as `torrent_closed`: start it to remove its data.
- Torrents kept by the seeding policy (`keep`/`defer`) are recorded before the Arr entry is removed and are marked in Downloads. Automatic deferred removal is not included yet.
- SQLite writes moved off the event loop and connections close deterministically. Job error codes are stored in structured form.

### Upgrade and rollback

The SQLite schema moves from 6 to 8: migration 7 adds the retained-torrent record and migration 8 adds job error codes. Configuration schema 4 is unchanged. Before upgrading from 2.0.4, create and verify a SQLite backup (`PRAGMA integrity_check` must return `ok`). Close old previews and generate fresh plans.

To roll back, stop CleanArr, keep the schema-8 database under a separate name, restore the schema-6 backup and start image 2.0.4. Version 2.0.4 cannot open a schema-8 database. See the [operations guide](https://github.com/mambastick/Cleanarr/blob/v2.1.0/docs/OPERATIONS.md) and [safety guide](https://github.com/mambastick/Cleanarr/blob/v2.1.0/docs/SAFETY.md).

Path checks compare the paths reported by the clients. Different mount points or symlinks for the same data are not detected, so all clients need a consistent path namespace.
