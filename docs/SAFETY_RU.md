# Модель безопасности

[English](SAFETY.md) · [Русский](SAFETY_RU.md)

CleanArr — orchestrator удаления, а не очиститель файловой системы. Он удаляет
только сущности, для которых настроенные сервисы предоставляют однозначную
цепочку владения. Отсутствующие или противоречивые доказательства приводят к
безопасному пропуску, а не к попытке угадать.

## Начальное состояние

Новая установка запускается с `DRY_RUN=true`. Dry-run выполняет discovery,
проверки владения, оценку seeding policy и полный preflight, но не вызывает
downstream-мутации. Не отключайте его, пока все сервисы не станут healthy, а
preview типичных movie, series, season и episode не подтвердят ожидаемое
владение.

Изменение переменной окружения не перезаписывает уже сохранённую runtime-
настройку. После каждого restore или migration проверяйте фактическое значение
на аутентифицированной странице Настройки или через configuration API.

## Обязательные доказательства владения

CleanArr использует точные provider identifiers и нормализованные пути для
поиска media entity во владеющем экземпляре Radarr или Sonarr. Torrent может
быть удалён, только когда история Arr предоставляет download identifier, а
настроенный клиент сообщает точно совпадающий нормализованный info hash.
Числовые ID Arr всегда ограничены своим instance и не считаются глобально
уникальными.

Операция завершается fail closed со структурированной причиной пропуска, если,
например:

- provider identifiers противоречат друг другу либо различаются доверенные пути из Arr;
- несколько Arr instances могут владеть событием без однозначного выбора;
- история Arr не доказывает download hash;
- torrent/file охватывает материалы вне запрошенного movie, series, season или
  диапазона episode;
- пути общие, torrent является паком либо cross-seeded данные нельзя безопасно
  изолировать;
- полученный от клиента путь пустой, относительный, содержит переход к родителю
  или указывает на корень файловой системы;
- downstream dependency или проверка аутентификации завершилась ошибкой.

## Проверка источника и физической области

Webhook cascade требует включённого настроенного Jellyfin. Сначала проверяется
точный item ID. Jellyfin 10.11.11 не поддерживает equality-фильтр provider IDs
на этом endpoint, поэтому fingerprint fallback использует полную pagination
с существующим лимитом 20 000 элементов. Лимита 1 000 items больше нет.
Изменение total отменяет весь проход и запускает его заново один раз;
повторное изменение даёт fail-closed. Некорректный/отсутствующий total,
неполные данные, каталог выше лимита или ошибка дают `source_unverifiable` и
блокируют cascade. Подтверждённые ручные сценарии доступны независимо.

Каждый preview и выполнение удаления данных получает полные приватные content
scopes всех настроенных downloader. Равные, родительские или дочерние области
другой раздачи, включая тот же hash в другом клиенте, дают `shared_path`,
когда обе области известны. Неполные сведения о файлах с проверенным root дают
`sibling_scope_unknown` для пересекающихся целей. Предпросмотр показывает имя,
клиент и hash непроверенной раздачи, не утверждая, что её файлы общие.
Независимые пути остаются доступными.
Раздача без metadata исключается из проверки пересечений только когда protocol
counters доказывают нулевой локальный payload; пустого file list недостаточно.
Для qBittorrent нужны `metaDL`, `total_size` -1 или 0, строго нулевые
completed/downloaded и конечный числовой progress 0.
Полностью неизвестный/ошибочный inventory даёт `ownership_unverifiable`.
Заблокированные цели сохраняют зависимые данные Arr/Seerr/Jellyfin. Один вызов
использует один fleet assessment и сверяет свежие metadata цели с его областью;
standalone guards сохраняются. Unknown existence не выдаётся за наличие раздачи
во всех клиентах и не разрешает зависимую очистку. Hash Radarr также не должен встречаться в полной
истории другого фильма любого настроенного instance, отфильтрованной по download ID.
Проверка не запрашивает историю каждого фильма и не вводит лимит 1 000 movies.
Общий hash блокируется как pack, а недоступная или неполная история даёт fail-closed.

Provider identifiers сравниваются независимо от системы путей Jellyfin.
Webhook file path не блокирует совпавший provider ID: путь Arr обозначает папку
в другой системе путей. Только доверенный ручной выбор из Arr получает внутренний
маркер для проверки конфликтов путей; входящий webhook не может его задать.
Совпадение точного пути остаётся слабым последним способом поиска.

Проверки сравнивают сообщённые POSIX paths и точные file lists. Они не читают
remote inodes и не разрешают разные bind-mount/symlink aliases. Клиентам нужна
согласованная система путей; неразрешённые физические aliases нельзя включать
в mutation-enabled operation. Hardlinks могут сохранять физические байты,
поэтому гарантии освобождённого места нет. Windows/UNC и некорректные пути —
unknown. Inventory rTorrent читается через один `d.multicall2` и
`directory.default` с проверкой строк и существующим лимитом 20 000 scopes.
Для закрытой раздачи консервативная область выводится из directory, name и
multi-file flag. Закрытая цель получает `torrent_closed`: откройте или
возобновите её в rTorrent, затем обновите предпросмотр. Само удаление данных
по-прежнему требует
непустой base path строго внутри текущего
`directory.default`; сам root, отсутствие отдельной подпапки и пути вне root
блокируются вместо recursive directory fallback.

## Preflight и порядок мутаций

Ручное удаление сначала возвращает точный план: media fingerprint, Arr instance,
torrent client/hash/path, downstream-мутации и все safety decisions.
Подтверждение привязано к SHA-256 canonical-плана. CleanArr отклоняет
отсутствующий, изменившийся или устаревший hash и пересчитывает план до первой
мутации.

Подтверждение одиночного удаления показывает выбранную область, названия торрентов (или хеши,
если названия недоступны), экземпляры сервисов, ID объектов и последствия
каждого шага. Удаление записи торрента отличается от удаления вместе со
скачанными файлами; очистка запросов, обращений и записей доступности Seerr,
а также отключение наблюдения Sonarr описываются отдельно. Для сохранённых
и заблокированных объектов показаны причины. Точный путь содержимого и папка
загрузки подписаны по-разному; отсутствующие данные остаются неизвестными.
План не обещает точное число освобождённых байтов: общие файлы и жёсткие ссылки
могут повлиять на физический результат.

Необязательные ссылки открывают настроенный сервис или известную карточку
материала в новой вкладке. Они не выполняют план. Внутренние адреса сервисов
могут работать только в сети администратора; RPC-адреса и URL с учётными данными
или query-параметрами не предлагаются как ссылки для браузера. Дополнительные
ID и пути раскрываются без вывода необработанных backend messages и токенов
подтверждения. Изменение показанных данных торрента или режима удаления файлов
требует обновлённого подтверждения, в том числе для планов до обновления версии.

Только устойчивые service identifiers, hashes и paths являются входными данными
для ownership. `display_name` — лишь presentation data. Batch сначала получает
mutation-free preview каждого child, связывает упорядоченные child plans одним
batch hash и перепроверяет их при submit/execution. Client idempotency key
возвращает ресурс только для того же canonical confirmed request; повторное
использование для другого request отклоняется. Заблокированные children остаются
видимыми, а batch может завершиться partial: общей all-or-nothing транзакции
между сервисами нет.

Удаление torrent выполняется до зависимых удалений из Arr, Seerr и Jellyfin.
Ошибка torrent блокирует эти зависимые мутации, чтобы доказательства владения
сохранились для безопасного retry. Успешные предыдущие действия и оставшееся
retry-state сохраняются в SQLite.

## Повторы и параллельность

Завершённые webhook events идемпотентно подавляются на семь дней. Уже
отсутствующий torrent или downstream entity считается идемпотентным результатом.
Partial failures и safety skips не помечаются завершёнными, потому что состояние
dependencies может измениться и следующий подтверждённый retry может стать
безопасным.

Если рестарт произошёл до потенциально мутирующей фазы manual job, CleanArr
перепроверяет сохранённый preflight. После этой точки job получает terminal
`interrupted_unknown` и не запускается автоматически. Exception или cancellation
webhook также оставляет durable tombstone `interrupted_unknown`; automatic
reconciliation/replay блокируется, поскольку нельзя доказать достигнутую
downstream-стадию.

Manual preflight повторяет только временные downstream/authentication ошибки
чтения в пределах существующего числа попыток. Ownership, общие пути,
неполные области, закрытые раздачи и другие safety blockers дают terminal
`unsafe_plan`: автоматический повтор не делает доказательства достоверными.
Ошибка durable retention recording также терминальна и блокирует зависимую
очистку.

Pause/resume в Downloads — обратимое действие, отдельное от удаления torrent
entry или data. Для него нужны fresh managed ownership evidence. Отсутствующие,
stale, partial или conflicting playback/watch/download observations являются
unknown: ими можно сортировать или объяснять рекомендацию, но нельзя разрешать
удаление.

Единый process-wide safety lock сериализует разрушительную webhook- и ручную
работу. CleanArr 1.0 поддерживает одну реплику приложения с одним SQLite state
volume; horizontal scaling и PostgreSQL/HA не входят в контракт 1.0.

## Checklist оператора

До включения мутаций:

1. Создайте и проверьте backup вне application state volume.
2. Оставьте dry-run включённым и проверьте каждый используемый media type и
   маршрут download client, включая паки и shared/cross-seeded пути.
3. Разберите каждое неожиданное совпадение или пропуск; не ослабляйте
   identifiers ради принудительного удаления.
4. Включайте мутации в контролируемое окно и сохраняйте предыдущий image/package
   вместе с соответствующим backup для rollback.
5. При расследовании используйте correlation ID, activity log, метрики и
   редактированный support bundle.
